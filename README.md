# Quarkus Queryable

Queryable is a Quarkus extension that adds annotation-driven collection filters
to Hibernate ORM REST Data with Panache.

Standard CRUD, count, OpenAPI and transaction handling are generated by
`quarkus-hibernate-orm-rest-data-panache`. Queryable contributes the collection
`GET` endpoint and its richer query language.

> Status: preview. The project is being prepared for Quarkiverse onboarding.

## What's new in 4.0.1

- Connect REST query parameters to existing Hibernate filters, including SQL
  subqueries, with [`@QFilter`](docs/modules/ROOT/pages/filters.adoc#hibernate-filters-and-sql-subqueries).
- Infer entity types from `QueryableFilter<T>` and `QueryableRsListener<T>`;
  existing `entityType()` overrides remain supported.
- Reject invalid creates and updates from lifecycle callbacks with REST
  exceptions; see [validation](docs/modules/ROOT/pages/lifecycle.adoc#validation-before-create-or-update).

Known limitation: `QOption.EXECUTE_ALWAYS` and `WITHOUT_PARAMETERS` are not
applied by this extension.

## Install

```xml
<dependency>
    <groupId>dev.queryable</groupId>
    <artifactId>quarkus-queryable</artifactId>
    <version>4.0.1</version>
</dependency>
```

Applications also select their JDBC driver and JSON extension, for example:

```xml
<dependency>
    <groupId>io.quarkus</groupId>
    <artifactId>quarkus-jdbc-postgresql</artifactId>
</dependency>
<dependency>
    <groupId>io.quarkus</groupId>
    <artifactId>quarkus-rest-jackson</artifactId>
</dependency>
```

## Minimal example

```java
@Entity
@QRs("/api/developers")
@QOrderBy("surname asc")
public class Developer extends PanacheEntityBase {

    @UuidGenerator
    @Id
    @QList
    public String uuid;

    @QLike
    public String name;

    @QLike
    public String surname;

    @QList
    public String team_uuid;

    @QLogicalDelete
    public boolean active = true;
}
```

The extension exposes:

```text
POST   /api/developers
GET    /api/developers/{id}
PUT    /api/developers/{id}
DELETE /api/developers/{id}
GET    /api/developers/count
GET    /api/developers?like.surname=pi
GET    /api/developers?obj.team_uuid=<uuid>
```

## Extension points

Custom filters go in `service.filters`:

```java
@ApplicationScoped
public class DeveloperFilter implements QueryableFilter<Developer> {

    @Override
    public void contribute(QueryableFilterContext<Developer> context) {
        // add Criteria API predicates
    }
}
```

REST lifecycle callbacks go in `service.rs`:

```java
@PrePersist
void audit(Developer developer) {
    developer.creationDate = LocalDateTime.now();
    developer.creationUser = identity.getPrincipal().getName();
}

@PostUpdate
void notify(Developer developer) {
    // external side effect, executed after commit
}
```

Queryable also supports existing Hibernate filters with
`@QFilter`; see [Query filters](docs/modules/ROOT/pages/filters.adoc).

Security remains standard Quarkus configuration:

```properties
quarkus.http.auth.permission.developers.paths=/api/developers/*
quarkus.http.auth.permission.developers.policy=authenticated
quarkus.http.auth.permission.developers-list.paths=/api/developers
quarkus.http.auth.permission.developers-list.policy=authenticated
```

## Build and test

```bash
mvn clean install
```

The reactor contains a complete Quarkus integration application. A standalone
consumer test simulates a separate real application:

```bash
mvn install -DskipTests
mvn -f consumer-tests/pom.xml test
```

## Release

Pushing a stable version tag matching the version in `pom.xml` triggers the
Maven Central release workflow. It uploads the signed artifacts and returns
without waiting for publication. Run the separate **Verify Maven Central
release** workflow manually with a version to check the parent, runtime, and
deployment artifacts. It checks once and fails if any artifact is unavailable;
if it fails, check the deployment in the Central Portal and run it again later.
Configure these repository Actions secrets before publishing: `NEXUS_USERNAME`,
`NEXUS_PASSWORD`, `GPG_PRIVATE_KEY`, and `GPG_PASSPHRASE`.

## Quarkus extension compliance

The implementation follows the main Quarkus extension principles:

- runtime and deployment artifacts are separate;
- application metadata is processed with Jandex during augmentation;
- resources are generated with Gizmo;
- runtime behavior is exposed through CDI extension points;
- native reflection requirements are registered at build time;
- application-specific security remains owned by Quarkus configuration;
- integration tests consume the runtime extension through normal Quarkus
  augmentation.

Remaining Quarkiverse onboarding work includes repository transfer, the
extension proposal, Ecosystem CI registration and documentation registration in
the Quarkiverse Antora playbook. See
[`docs/modules/ROOT/pages/testing.adoc`](docs/modules/ROOT/pages/testing.adoc).
